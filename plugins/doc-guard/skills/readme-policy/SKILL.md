# README の書き方

## 原則

README は**評価と最初の一歩のための文書**。「これは何か」「自分に要るか」「どう動かすか」の 3 つに答えたら終わり。動かした後に必要になる知識は README に置かない。

想定読者は未来の自分と、たまたま見に来た人。探しにくさの方が短さより高くつく。

## 構成（この順序で固定）

1. `# プロジェクト名` — H1 はこれだけ
2. **1〜3 行の説明** — 何をするものか。スクロールせずに読み切れること
3. デモ / スクリーンショット / 公開 URL（あれば）
4. `## 依存` — 実行に必要なものとバージョン下限
5. `## セットアップ` — コピペで動く最短手順
6. `## 使い方` — 最小の例から。オプションの網羅は避ける
7. `## 制限` — 既知の制約（あれば）
8. `## ドキュメント` — `docs/` 配下へのリンク（分割した場合のみ）
9. `## ライセンス` — 1 行 + LICENSE への相対リンク

## 何を外に出すか

まず各記述を末尾の「記述の基準」で判定し、「書かないもの」に当たる記述は README からも `docs/` からも消す。

残った節に**「使い始める前に読む必要があるか？」**を問う。NO なら README から出す。

| 内容 | 行き先 |
|---|---|
| 踏み抜くと運用を誤る制約や罠 | README の `## 制限`。開発時にしか関わらないものは `docs/development.md` |
| 任意機能の設定（外部サービス連携など） | `docs/<機能名>.md` |
| モジュールの責務、開発者向けの検証手順、テストの回し方 | `docs/development.md` |
| 貢献手順、行動規範、脆弱性報告 | `CONTRIBUTING.md` / `CODE_OF_CONDUCT.md` / `SECURITY.md` |

`docs/` への相対リンクは GitHub 上でそのまま動く。

### 切り出したファイルの見出し

- **1 つの節だけを切り出す場合** — その節の `##` を `#` に上げ、配下の `###` も 1 段上げる
- **複数の節をまとめる場合** — まとめ全体を表す `#` を新しく付け、元の `##` はそのまま残す。このとき **H1 と直下の H2 が同じ語にならない H1 を選ぶ**。`# 隔離とセキュリティ` の直下に `## 隔離` が来る形は不可で、`# 実行環境と権限` のように、まとめた節のどれとも重ならない名前にする
- README の `## ドキュメント` 節に書くリンク文言は、切り出したファイルの H1 と一致させる

## 外部サービスの手順は書かない

公式ドキュメントに載っている操作手順（アカウント登録、鍵の生成、設定画面の場所、ボタンの名前）は書き写さず、**公式ページへリンクする**。二重管理になるうえ、相手の UI 変更で確実に腐る。腐ったことにこちらは気づけない。

代わりに、**そのリポジトリでしか決まらない値**を書く。

| 書かない（公式へリンク） | 書く（このリポジトリ固有） |
|---|---|
| 「Settings → Developer settings → New GitHub App」 | 与える権限の一覧と、なぜその権限が要るか |
| 「Generate a private key を押す」 | 鍵の置き場所、パーミッション、設定ファイルのキー名 |
| 「Install App から対象を選ぶ」 | 設定後の確認コマンドと、期待される出力 |
| 公式の既定値のまま進む箇所 | **既定から変える必要がある箇所**（例: Webhook を切る） |

判断は「公式ドキュメントの URL を貼れば済むか？」。済むなら貼るだけにする。

例外は、公式に書いてあっても踏み抜きやすい帰結（例: GitHub App が作った PR は Actions を発火しない）。これは手順ではなく**このリポジトリの運用への影響**なので書く。

## ファイル一覧は書かない

`ls` や `tree` を叩けば分かる情報は書かない。ファイルが増減するたびに手で直す必要があり、直し忘れても誰も気づかない。

載せるのは**名前から読み取れない責務**だけ。

| 書かない | 書く |
|---|---|
| `poll.sh  エントリポイント` — 名前とセットアップ手順から分かる | `lib/discover.sh  タスク検出（ラベル / コメント）` — 名前だけでは担当範囲が分からない |
| ディレクトリツリーの再現 | 実行時にしか現れないディレクトリの中身（`logs/<task-id>/` に何が入るか） |
| README や他のドキュメントで既に説明したファイル | どこにも説明がないモジュールの役割 |

見出しは「ファイル構成」ではなく「**モジュールの責務**」にする。構成図に見えると、あとから自明なファイルを足したくなる。

## 文体

1 文を短くする。過不足なく書き、装飾しない。

- **理由を括弧に押し込まない。** 独立した文にする
- **1 文に節を詰め込まない。** 「〜し、〜して、〜する」は切る
- **文脈から自明な語を落とす。** 直前に出た主語・ファイル名・設定名は繰り返さない
- **受け身より能動。** 「実行され、囲われている」→「実行する。囲いは次の多層」

| 冗長 | 簡潔 |
|---|---|
| 認証を一切持たない | 認証を持たない |
| worktree そのものではなく | worktree ではなく |
| 指定した場合は警告を出すだけで、PR 自体は成立させる | 指定に失敗しても、警告を出すだけで PR は成立させる |

推敲の効果は行数では測れない。1 文を短くすると改行が増え、行数はむしろ変わらない。

## 数値ガード

- **150 行**を超えたら分割を検討する
- `## ` 見出しが **8 個**を超えたら分割する
- 手書きの目次は作らない（GitHub が見出しから outline を自動生成する）

## 採らないもの

- バッジ — 個人リポジトリでは情報量に対して場所を取りすぎる。CI が回っていて意味がある場合のみ
- Contributing / Support / Roadmap の節 — 共同開発しているリポジトリでのみ書く
- 「長すぎるより短すぎる方が悪い」という考え方

## 手順（既存の README を整理するとき）

1. **測る。** `wc -l README.md` と `grep -c '^## ' README.md`。ガードを超えているか数字で確認する
2. **節ごとに分類する。** 上の「何を外に出すか」で行き先を決める。判定は節単位で、迷ったら「使い始める前に読むか」に戻る
3. **移す。** `docs/` へ切り出し、README には `## ドキュメント` 節でリンクする。見出しは「切り出したファイルの見出し」に従う
4. **文体を整える。** 移した先も含め、「文体」に従って推敲する
5. **取りこぼしを確認する。** 分割前の見出しが全部どこかに残っているか照合する。

   ```bash
   git show HEAD:README.md | grep -E '^#{2,3} ' | sed 's/^#* //' | while IFS= read -r h; do
     grep -qrF "$h" README.md docs/ || echo "LOST: $h"
   done
   ```
6. **測り直す。** README とドキュメント全体の行数を出し、削減量を報告する
7. **リンクを検証する。** markdown リンクの参照先だけを抜き出して確かめる。素の URL を `grep` すると、表セルやコード中の例示 URL を拾って誤検知する。

   ```bash
   grep -rhoE '\]\([^)]+\)' README.md docs/*.md | sed -e 's/^](//' -e 's/)$//' | sort -u |
   while read -r t; do
     case "$t" in
       http*) printf '%s  %s\n' "$(curl -sSL -o /dev/null -w '%{http_code}' --max-time 20 "$t")" "$t" ;;
       \#*)   ;;
       *)     [ -e "$t" ] && echo "OK   $t" || echo "MISS $t" ;;
     esac
   done
   ```

## 注意

- 分割は**移動**であって削除ではない。内容を落とす場合は、何をなぜ落としたか明示して承認を得る
- `docs/` 配下は README のガード（150 行 / H2 8 個）の対象外。参照用なので網羅してよい
- README を短くするために説明を薄めない。節を移すことで短くする
